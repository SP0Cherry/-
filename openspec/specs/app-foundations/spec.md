# app-foundations Specification

## Purpose

为 CampusClaw 提供课堂可复现的运行地基：幂等的预置演示数据、基于 Docker Compose 的一键启动、无需登录的 GET /health 健康检查，以及密钥只来自服务端环境变量的配置管理。

## Requirements

### Requirement: 预置演示数据

系统 MUST 提供可重复执行的种子初始化能力，预置至少两个班级（A 班、B 班）和用于演示权限隔离的账号：每个班级各一名教师与一名学生（共四个账号），并为 A 班预置至少一条示例材料；重复执行 MUST NOT 产生重复数据或重复账号。

#### Scenario: 首次初始化

- **WHEN** 在空数据库上执行种子初始化
- **THEN** 系统创建 A 班、B 班、四个演示账号（teacher_a、student_a、teacher_b、student_b，密码均以加盐哈希存储）以及 A 班的一条示例材料，各账号角色与班级归属正确

#### Scenario: 重复执行幂等

- **WHEN** 在已有种子数据的数据库上再次执行种子初始化
- **THEN** 系统不重复创建班级、账号或材料，已有数据保持不变，命令成功结束

#### Scenario: 预置账号可演示隔离场景

- **WHEN** 分别使用 student_a 与 teacher_b 等预置账号登录
- **THEN** 可直接复现"学生上传被拒（403）"与"A 班账号访问不到 B 班材料（404）"的课堂演示场景

### Requirement: 预置 A 班示例技能

种子初始化 MUST 在 A 班预置两份启用状态的示例技能：`数学解题引导` 与 `语文解题引导`。两份技能 MUST 使用合法 SKILL.md 元数据（包含必填的 `名称`、`适用条件`、`启用`），正文 MUST 说明只引导学生检查下一步、不直接给出最终答案，并引用内置工具 `knowledge_search`。

预置技能 MUST 只归属 A 班，MUST NOT 自动出现在 B 班。重复执行种子初始化 MUST 保持幂等：已有同名技能 MUST 保持不变，MUST NOT 产生重复记录。

#### Scenario: 首次种子初始化写入两份技能

- **WHEN** 在空数据库上执行种子初始化
- **THEN** A 班存在 `数学解题引导` 与 `语文解题引导` 两份启用技能，B 班不存在这两份技能

#### Scenario: 重复种子初始化保持幂等

- **WHEN** 在已包含这两份技能的数据库上再次执行种子初始化
- **THEN** 技能数量不增加，已有技能内容与启用状态保持不变

#### Scenario: 预置技能可被学生选择

- **WHEN** A 班学生登录并请求本班可选技能列表
- **THEN** 列表包含这两份预置技能，且可用于提问选择

### Requirement: 预置 A 班示例提示词模板

种子初始化 MUST 在 A 班预置一份启用状态的示例提示词模板。该模板 MUST 使用合法模板元数据（包含必填的 `名称` 与 `启用`），正文 MUST 至少使用一个固定占位符，并以附加规程形式约束回答方式（例如先给结论再列要点）。

预置模板 MUST 只归属 A 班，MUST NOT 自动出现在 B 班。重复执行种子初始化 MUST 保持幂等：已有同名模板 MUST 保持不变，MUST NOT 产生重复记录。

#### Scenario: 首次种子初始化写入模板

- **WHEN** 在空数据库上执行种子初始化
- **THEN** A 班存在一份启用状态的示例提示词模板，B 班不存在该模板

#### Scenario: 重复种子初始化保持幂等

- **WHEN** 在已包含该模板的数据库上再次执行种子初始化
- **THEN** 模板数量不增加，已有模板内容与启用状态保持不变

#### Scenario: 预置模板可被学生选择

- **WHEN** A 班学生登录并请求本班可选模板列表
- **THEN** 列表包含该预置模板，且可用于提问选择

### Requirement: Docker Compose 一键启动

系统 MUST 提供容器化启动方式：通过 Docker Compose 可一条命令启动应用并在宿主机发布访问端口；SQLite 数据库文件与材料上传目录 MUST 通过卷持久化，容器重建后数据不丢失；运行所需密钥 MUST 通过环境变量注入，MUST NOT 烘焙进镜像。

#### Scenario: 全新环境一键启动

- **WHEN** 在仅安装了 Docker 与 Docker Compose 的机器上配置好环境变量并执行 `docker compose up`
- **THEN** 应用自动完成建表与种子初始化并在发布端口提供服务，浏览器可打开登录页，日志中无启动错误

#### Scenario: 容器重建后数据保留

- **WHEN** 在运行中上传新材料后停止并删除容器，再重新 `docker compose up`
- **THEN** 之前创建的账号、材料元数据与已上传文件仍然存在且可下载

### Requirement: 健康检查接口

系统 MUST 提供无需认证的 `GET /health` 接口，用于容器编排与课堂环境自检；接口 MUST 反映应用与数据库依赖的真实可用性。

#### Scenario: 应用与数据库正常

- **WHEN** 在应用正常运行、数据库可访问时请求 `GET /health`（不带登录 Cookie）
- **THEN** 系统返回 200 与表明健康的 JSON 状态体，且该请求不触发登录重定向

#### Scenario: 数据库不可用时告警

- **WHEN** 应用进程存活但数据库无法访问时请求 `GET /health`
- **THEN** 系统返回 503 与表明依赖异常的 JSON，而不是仍返回健康

### Requirement: 密钥与配置只来自服务端环境变量

系统 MUST 只从服务端环境变量（或服务端读取、不提交仓库的环境文件）获取会话签名密钥等敏感配置；密钥 MUST NOT 硬编码在源码中、MUST NOT 写入镜像、MUST NOT 出现在发给浏览器的任何内容里；生产模式下缺少必要密钥时应用 MUST 拒绝启动。

#### Scenario: 缺少密钥时快速失败

- **WHEN** 应用以生产模式启动且未配置会话签名密钥等必要环境变量
- **THEN** 应用在启动阶段报错退出，不以弱默认密钥或空密钥继续运行

#### Scenario: 仓库与镜像不含真实密钥

- **WHEN** 检查代码仓库中的配置样例或构建出的容器镜像
- **THEN** 只能看到占位符（如 `.env.example` 中的说明性示例），不存在可用于签名会话的真实密钥
